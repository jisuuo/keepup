## 1. 오늘의 목표

curl 구간 측정 스크립트를 만들어 `/actuator/health`를 잰다. 클라이언트(curl)가 본 시간과 서버 필터(`RequestLogFilter`)가 찍은 시간을 requestId로 맞대서, 차이가 어느 구간에서 생기는지 본다.

오늘의 질문(Q1): curl이 잰 시간과 서버 로그 시간의 차이는 어느 구간에서 생기고, localhost에서는 얼마나 될까?

요청이 TCP 연결부터 톰캣이 처리하기까지 실제로 어떤 과정을 거치는지 알고 싶었다. 특히 그중 어디까지가 OS 커널의 일이고 어디부터가 톰캣의 일인지 정확히 나누고 싶었다.

## 2. 따라간 요청

### curl 시간 변수는 누적값이다

`curl -w`의 시간 변수는 모두 curl이 시작한 시점부터의 누적값이다. 구간은 뺄셈으로 만든다. 스크립트(`scripts/curl-timing.sh`)는 이렇게 나눴다.

| 열 | 계산 | 뜻 |
|---|---|---|
| dns | `namelookup` | 이름 → IP 주소 |
| tcp | `connect - namelookup` | TCP 3-way handshake |
| tls | `appconnect - connect` | HTTPS일 때만 (http면 0) |
| wait | `starttransfer - pretransfer` | 요청 전송 + 서버 안 전체 + 첫 바이트 도착 |
| body | `total - starttransfer` | 나머지 응답 수신 |

서버 로그의 ms와 비교할 대상은 `total`이 아니라 `wait`다. DNS와 TCP 연결은 서버 필터가 시작되기 훨씬 전에 끝나기 때문이다.

### 요청 하나의 길

```
 curl                         OS 커널 (서버 쪽)              톰캣
 ────                         ─────────────────              ────
 DNS (localhost → 주소)
 SYN      ────────────▶      SYN 받음
          ◀────────────      SYN-ACK
 ACK      ────────────▶      handshake 끝 → accept 큐에 넣음
 connect ● (tcp 끝)
 pretransfer ●
 요청 전송 ────────────▶     소켓 버퍼
                                    └──────────────▶  ① accept()
                                                      ② Poller → 작업 큐 (워커가 바쁘면 대기)
                                                      ③ 워커 스레드가 HTTP 파싱
                                                      ④ 내 필터보다 앞선 필터들
                                                      ┌───────────────────────────┐
                                                      │ RequestLogFilter start    │ ← 서버 로그 ms
                                                      │ 컨트롤러 · DB 체크         │
                                                      │ finally: 로그 기록        │
                                                      └───────────────────────────┘
                                                      ⑤ 응답 마무리 · 소켓 쓰기
 starttransfer ● ◀──────────────────────────────────  첫 바이트
 total ●
```

그림의 ①~⑤는 측정이 아니라 톰캣 구조(DAY 003에서 읽은 소스)를 바탕으로 그린 것이다. 서버 로그 ms에는 ①~⑤가 들어가지 않는다. curl의 `wait`에는 들어간다.

## 3. 측정값

환경: macOS, localhost, Spring Boot 4.1.1, curl 8.7.1. 앱 재기동 직후부터 쟀고, 각 묶음은 1회 실행이다. 단위는 ms.

### 재기동 직후 첫 요청 + 이후 10회 (`localhost`)

| 순서 | curl wait | 서버 로그 | 차이 (필터 밖) |
|---|---|---|---|
| 재기동 후 첫 요청 | 180.81 | 86 | 약 95 |
| 2 | 10.51 | 9 | 약 1.5 |
| 3 | 8.30 | 7 | 약 1.3 |
| 4~11 | 2.44~2.84 | 1~2 | 약 0.5~1.6 |

- dns 0.01, tcp 0.20~0.24, tls 0이었다. 첫 요청도 tcp는 0.23으로 다른 요청과 같았다.
- 11건 모두 응답 헤더의 `X-Request-Id`와 서버 로그의 requestId가 맞았다.

### `127.0.0.1` vs `localhost` (웜업 후, 각 10회)

|---|---|---|---|---|---|

| 내 예측 | 결과 |

| `localhost`는 `127.0.0.1`로 연결될 것 | 틀렸다. 11회 모두 `::1`(IPv6)이었다 |

## 4. 배운 것: 한 층 아래

### TCP 연결은 OS가 맺고, 톰캣은 accept()부터 손댄다

3-way handshake(SYN → SYN-ACK → ACK)는 톰캣이 아니라 OS 커널이 한다. 커널은 연결을 다 맺어 accept 큐에 넣어 두고, 톰캣은 `accept()`로 그걸 꺼내 간다. 그래서 순서는 항상 curl의 connect가 끝난 **뒤에** 톰캣의 accept가 온다. 이건 오늘 직접 잰 것이 아니라 일반적으로 알려진 TCP 동작이다. DAY 003에서 "accept 큐에 선 요청은 connect가 즉시 끝났다"고 관찰한 것과도 맞는다.

그 결과 어디서 막히느냐에 따라 늘어나는 열이 다르다.

| 어디가 막혔나 | 늘어나는 열 |
|---|---|
| accept 큐가 꽉 참 → handshake가 끝나지 못함 | `tcp` (DAY 003: 2.2~6.1초) |
| accept() 이후 어딘가 늦음 (주로 워커가 다 바빠 작업 큐에서 대기) | `wait` |

처음에 나는 accept가 connect 전이라고 답했다가 고쳤다. 헷갈렸다.

### 첫 요청의 느림은 필터 안팎 양쪽에 있었다

첫 요청에서 필터 안이 86ms, 필터 밖이 약 95ms였다. 처음에는 TCP 연결 시간이 원인일 거라고 생각했지만, `tcp` 열이 첫 요청에서도 0.23ms라 이 가설은 데이터로 기각됐다. 필터 밖 95ms의 후보는 ① accept, ② Poller·작업 큐, ③ HTTP 파싱, ④ 앞선 필터, ⑤ 응답 마무리다. 나눠 재지는 않았다.

어디서 왔을지는 아직 따로 추측하지 못했다(5절).

### `::1`은 IPv6의 "나 자신"이다

- `127.0.0.1`(IPv4)과 `::1`(IPv6)은 둘 다 루프백 주소다. 형식만 다르고 뜻은 같다. `::1`은 `0000:…:0001`에서 연속된 0을 줄여 쓴 것이다.
- 내 `/etc/hosts`에는 `localhost`가 두 주소에 모두 매핑돼 있었다. curl은 `::1`로 연결했다. IPv6를 먼저 시도하는 동작(Happy Eyeballs) 때문이라고 이해했지만, curl 내부 동작은 확인하지 않았다.
- 자바는 8080을 IPv6 소켓 하나로 열고 있었고(`lsof`: `IPv6 TCP *:8080 (LISTEN)`), 이 소켓으로 `127.0.0.1` 요청도 받았다.

## 5. 막힌 것 / 다음에 볼 것

- **첫 요청의 필터 밖 약 95ms가 어느 구간인지** 모른다. ①~⑤를 나눠 재야 한다.
- **서버 로그가 정수 ms다.** `/ 1_000_000`에서 소수점이 잘려서, 웜업 후의 "필터 밖 약 1ms"는 오차 범위 안이다. μs로 찍어야 비교할 수 있다.
- **웜업은 첫 요청 하나로 끝나지 않았다.** 2, 3번째도 10ms, 8ms였고 4번째부터 약 2.5ms로 안정됐다. 이유는 모른다.
- **`127.0.0.1`의 dns가 `localhost`보다 길었다**(0.06~0.10 vs 0.01). 숫자 주소인데도 그랬다. 이유는 확인하지 않았다(차이는 0.1ms 미만).
- **처리 스레드가 exec-2, 4, 6, 8, 10 순으로 짝수 번호만 돌았다.** 이유는 모른다.
- 모든 값은 묶음당 1회 실행이다.
